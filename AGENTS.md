# Project instructions

- Keep `README.md` and this file aligned with every feature or dependency change. Keep all third-party credits and license references in README.
- Keep the application fully static. GitHub Pages hosts the built site at `/chesstrapboard/` on `https://lukas.zapletalovi.com`; runtime assets come from this repository.
- Maintain one full-game opening trainer. Opening selection is optional: choose randomly when unset, prefer a line compatible with White's first move, and allow the first board interaction or New game to start play. The CPU follows the chosen line while applicable, then any matching position-indexed database continuation, and only then normal engine play. It may seek engine-validated trap opportunities from its third move even while book moves exist, and grades moves only afterward. Optional live evaluation may show an ungraded score during play and defaults off.
- Keep CPU difficulty separate from the frequency and size of deliberate mistake attempts. Offer Off, 25%, 50%, 85%, and 95% attempt chances, with 95% selected for new visitors. Validate generated candidate moves and replies with `chess.js`, then confirm the advantage with a separate engine search from the resulting position; when no candidate qualifies, prefer a selected-line move, then a legal database move, then a normal engine move. For normal engine play, randomly choose between the top two legal centipawn moves only when their scores differ by at most 20 centipawns; leave mate scores alone. Count attempted checks separately from generated opportunities and keep the postgame console diagnostics accurate. Keep the long settings explanations, including opportunity-size ranges, in hover text.
- Keep Lichess opening source TSV and deterministic, browser-ready processed `openings.json` and `book.json` in Git. Build the position book from validated source moves, merge transpositions by four-field FEN, and verify both outputs in CI. Data updates are explicit.
- Keep Take back between New game and End game & Analyze. It undoes the player's latest move and any CPU reply, even if the game just ended; cancel searches and review, drop opportunity checks and generated records for undone moves, recompute opening progress, and leave the player to move.
- Keep the browser engine files in Git. Record the exact upstream release, checksums, GPL license, and corresponding source location.
- Attribute every external package, dataset, sound, and artwork with verified license terms before adding it.
- The move tap and opportunity chime are synthesized in `src/sound.ts`; no external audio assets are included. Both default on with shared volume at 50%. The Opportunity hint & sound toggle controls both the chime and the brief cue above the board. Only a validated deliberate CPU opportunity may trigger them; keep opportunity marks for postgame review.
- Keep one clickable move list for play and postgame review. Place the always-visible evaluation card above Moves and the selected move's suggested line directly below Evaluation; clip the line to one row and expose its full text on hover. Scrub the validated principal variation on the board as the pointer moves across the line, then restore the selected game position shortly after pointer leave without changing move selection. Keep review progress and navigation below Copy PGN. Use sparse postgame `!`, `!!`, `?`, and `??` marks: mark losses of at least 200 or 500 centipawns, include clearly missed or newly allowed mates, and praise an engine-best move only when the next-best line is at least 180 or 400 centipawns worse. Search two principal variations for review, and do not mark moves without enough scores to justify a mark. Underline only generated CPU opportunity moves after review; mark the player's reply `!` when found or `?` when missed, overriding its general annotation. Analyze reviewed positions from latest to earliest, store results by original ply, and print diagnostics to the JavaScript console. Re-evaluate candidates after the game, allow modest score drift, and leave vanished advantages unconfirmed. Preserve wheel and arrow-key navigation, a blank evaluation score by default, and one Copy PGN button without a visible notation box. Keep the last live score visible while the next position is evaluated. Keep Hint beside Copy PGN; validate its engine move with `chess.js`, mark its source and destination on the board with distinct colors, and clear stale hints when the position changes. The board colors and button state are enough feedback; do not add a separate hint status line. Cancel stale live searches when the viewed position changes.
- Keep `.github/FUNDING.yml` limited to the `lzap` GitHub Sponsors username, matching the location and filename GitHub recognizes.
- Use `chess.js` as the authoritative rules and PGN implementation. Validate all book and engine moves through it.
- Run `npm run check`, focused tests, `npm run verify:data`, `npm run verify:engine`, `npm run verify:licenses`, and `npm run build` for code changes. Include a real-browser check when engine or Pages asset paths change.
- Follow the user's global Git instructions: pull `main` before commits, inspect recent commit style, make small reviewable commits, and ask before any push while showing changed files and destination.
