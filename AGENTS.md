# Project instructions

- Keep `README.md` and this file aligned with every feature or dependency change. Keep all third-party credits and license references in README.
- Keep the application fully static. GitHub Pages hosts the built site at `/chesstrapboard/` on `https://lukas.zapletalovi.com`; runtime assets come from this repository.
- Maintain one full-game opening trainer. Opening selection is optional: choose randomly when unset, prefer a line compatible with White's first move, and allow the first board interaction or New game to start play. The CPU follows the chosen opening while applicable, may seek engine-validated trap opportunities from its third move, and grades moves only afterward. Optional live evaluation may show an ungraded score during play and defaults off.
- Keep CPU difficulty separate from the frequency and size of deliberate mistake attempts. Offer Off, 25%, 50%, 85%, and 95% attempt chances, with 95% selected for new visitors. Validate generated candidate moves and replies with `chess.js`, then confirm the advantage with a separate engine search from the resulting position; fall back to a book move or normal engine move when no candidate qualifies. Count attempted checks separately from generated opportunities and keep the postgame console diagnostics accurate. Keep the long settings explanations in hover text.
- Keep Lichess opening source TSV and deterministic, browser-ready processed data in Git. Data updates are explicit; CI verifies the processed files match their source.
- Keep the browser engine files in Git. Record the exact upstream release, checksums, GPL license, and corresponding source location.
- Attribute every external package, dataset, sound, and artwork with verified license terms before adding it.
- The move tap and opportunity chime are synthesized in `src/sound.ts`; no external audio assets are included. Both default on with shared volume at 50%. The Opportunity hint & sound toggle controls both the chime and the brief cue above the board. Only a validated deliberate CPU opportunity may trigger them; keep opportunity marks for postgame review.
- Keep one clickable move list for play and postgame review. Place the always-visible evaluation card above Moves and the selected move's suggested line directly below Evaluation; clip the line to one row and expose its full text on hover. Keep review progress and navigation below Copy PGN. Underline only generated CPU opportunity moves after review; mark the player's reply `!` when found or `?` when missed, independently of its general engine grade. Print review diagnostics to the JavaScript console. Re-evaluate candidates after the game, allow modest score drift, and leave vanished advantages unconfirmed. Preserve wheel and arrow-key navigation, a blank evaluation score by default, and one Copy PGN button without a visible notation box. Keep Hint beside Copy PGN; validate its engine move with `chess.js`, mark its source and destination on the board with distinct colors, and clear stale hints when the position changes. Cancel stale live searches when the viewed position changes.
- Keep `.github/FUNDING.yml` limited to the `lzap` GitHub Sponsors username, matching the location and filename GitHub recognizes.
- Use `chess.js` as the authoritative rules and PGN implementation. Validate all book and engine moves through it.
- Run `npm run check`, focused tests, `npm run verify:data`, `npm run verify:engine`, `npm run verify:licenses`, and `npm run build` for code changes. Include a real-browser check when engine or Pages asset paths change.
- Follow the user's global Git instructions: pull `main` before commits, inspect recent commit style, make small reviewable commits, and ask before any push while showing changed files and destination.
